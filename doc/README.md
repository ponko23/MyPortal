# MyPortal プロジェクトドキュメント

## プロジェクトの目的

MyPortal は、自分で利用する便利な小規模 Web アプリを一つのサイト配下に構築するための共通基盤を継続的に開発するプロジェクトです。

- **各アプリの特性**: 単機能・小規模なものを基本とします
- **統合方針**: 巨大な一つの Web アプリケーションに統合することを目的としません
- **配置方式**: 同一サイト・同一 Origin 上に配置しながら、各アプリは独立したアプリケーションとしてビルド・デプロイできる構成を目指します

## 利用方法

- **主要な利用端末**: iPhone
- **利用形態**: Safari から PWA としてホーム画面に追加し、アプリアイコンから個別アプリを起動
- **代替手段**: iOS 版 Chrome からブックマーク経由での利用
- **アクセス方法**: MyPortal トップページから各アプリへのリンクを提供しますが、個別アプリは直接 URL をブックマークして利用することも想定

## 技術スタック

| 項目 | 技術 |
|------|------|
| ランタイム | .NET 10 |
| フロントエンドフレームワーク | Blazor WebAssembly |
| 言語 | C# |
| バージョン管理 | GitHub |
| ホスティング | GitHub Pages |
| UI 設計思想 | Blazor ベストプラクティス + React などの設計思想も活用 |

**特に重視する点**: UI コンポーネントとアプリケーション状態・ロジックの適切な分離

## リポジトリ構成

```
MyPortal/
├─ doc/                           # プロジェクト全体のドキュメント
├─ src/                           # MyPortal 本体のソース
│  └─ トップページと各アプリへのリンク
├─ common/
│  ├─ doc/                        # 共通基盤の設計・ルール・ナレッジ
│  └─ src/                        # 共通基盤のソース
└─ apps/
   └─ <app>/
      ├─ doc/                     # 各アプリのドキュメント
      └─ src/                     # 各アプリのソース
```

### 各ディレクトリの役割

#### `doc/`
MyPortal プロジェクト全体に関するドキュメント。以下の内容を対象とします。

- プロジェクトの目的
- 全体的な設計方針
- リポジトリの構成
- 開発・Issue・PR の運用方針
- ドキュメント管理方針
- 共通する技術上の知識・判断
- 将来的な拡張方針

#### `src/`
MyPortal 本体のソース。トップページとして各アプリへのリンクなどを提供するアプリケーション。個別アプリとは異なり、MyPortal そのものを構成するアプリケーション。

#### `common/`
複数のアプリから利用する共通基盤。

```
common/
├─ doc/    # 共通基盤の設計・ルール・ナレッジ
└─ src/    # 共通基盤のソース（複数 DLL に分割可能）
```

共通基盤には、単純な UI 部品だけではなく、複数の UI フレームワークから利用できるアプリケーション層も含めます。

#### `apps/`
個別の Web アプリケーション。各アプリは独立したアプリケーションとして管理します。

```
apps/
└─ <app>/
   ├─ doc/     # 各アプリのドキュメント
   └─ src/     # 各アプリのソース
```

各アプリは必要な共通基盤の機能だけを参照することを基本とします。

## 共通基盤の設計方針

### 機能分離
共通基盤は機能単位で分離し、必要な機能だけを依存関係に追加できる構成を目指します。

### UI とアプリケーションロジックの分離
将来的に WinUI など、Blazor とは異なる UI フレームワークからもアプリケーションロジックを利用できる構成を目指します。

```
UI Component
    │
    ├─ State
    ├─ Action
    └─ Validation
          │
          ▼
    Application / Domain
          │
          ▼
      Persistence
```

- **UI コンポーネント**: State と Action を受け取り、表示・操作する役割を中心
- **ViewModel**: 必要に応じて State / Action と UI の DataBinding を仲介するアダプター
- **アプリケーションロジック**: ViewModel に集約しない

### Validation
Validation は ViewModel に集約しない方針。以下の責務を分離します。

- アプリケーション・ドメイン上の入力値が妥当かを判定する処理（UI フレームワーク非依存）
- UI 上でいつ・どのようにエラーを表示するか（UI フレームワーク依存）

## データ保存方針

### ローカルデータ保存（初期段階）
各アプリのデータは原則として利用端末側に保持します。基本的な永続化先は以下を検討。

```
SQLite
  ↓
OPFS
```

### データ分離とスケーラビリティ
- アプリごとにデータを分離することを基本
- 必要に応じて共通設定などを共有する余地を残す
- UI やアプリケーションロジックから永続化方式を直接参照しない構造で、将来的な拡張（Google Drive バックアップなど）に対応可能にする

### 将来的な拡張余地
以下の機能は現時点の初期実装対象には含めません。

- Google Drive によるバックアップ
- 複数ユーザー間でのデータ共有
- 認証
- バックエンドでのデータ永続化
- Cloudflare などのバックエンド機能

まずは「静的配信 + ローカルデータ保存」を成立させることを優先します。

## ビルド・デプロイ方針

### 独立したビルド・デプロイ
個別アプリは可能な限り独立してビルド・デプロイできる構成とします。

例：
```
common
   ↓
appA
```

という依存関係の場合、appA は必要な common の機能を参照して単独でビルド・デプロイできることを目指します。

### 共通基盤の変更時の対応
共通基盤に変更が入った場合は、その変更の影響を受けるアプリを再ビルド・再デプロイすることを許容します。

### GitHub Pages への公開
ビルド成果物の配置方法は、リポジトリのソース構造とは分離します。
GitHub Actions 等の CI/CD 設定でビルド・公開処理を構築する際に決定します。

## Issue / PR を起点とした開発

### 基本的な開発フロー

1. Issue を起点に開発を始める
2. 設計・仕様を検討し、Issue に整理
3. 実装（人間が行ってもアクセシビリティ、GitHub Copilot などの AI を利用してもよい）
4. Pull Request を作成
5. レビュー
6. Merge

### 実装方法の選択
実装自体は人間が行っても、GitHub Copilot、Codex などの AI に委任しても構いません。

## ドキュメント管理方針

### ドキュメント管理の基本原則
このリポジトリでは、設計上の重要な判断や継続的に参照する知識をドキュメントとして管理します。

### チャット議論の反映
チャットなどで行った設計議論についても、重要な内容は最終的にリポジトリのドキュメントへ反映します。

### 有効な設計方針の優先
ドキュメント更新時には、現在有効な設計方針を正とします。以前の議論によって記載されている内容であっても、現在の方針と矛盾するもの、不要になったもの、無効になったものは削除・修正します。

### 初期段階での方針
現時点で必要性が確認されていない設計書を大量に作成しないこととします。
